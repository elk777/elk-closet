# AI 接口提速方案

> 对象：添加衣物识图（`POST /garments/recognize`）、首页今日推荐（`POST /recommend/today`）、智能搭配（`POST /recommend/outfits`）。
> 基线日期：2026-10-28。测量环境：本机 dev（NestJS 常驻 3100）+ demo 账号（26 件种子衣物）+ lucky0625 / 42w 渠道。

---

## 1. 现状基线

| 接口 | 场景 | 实测耗时 |
|---|---|---|
| 识图 `recognize` | 同一张 1024px 衣物图，5 次 | **7.0s / 22.7s / 30.7s / 33.4s / 35.8s** |
| 今日推荐 `recommend/today` | 命中当日时段缓存 | **0.02s / 0.24s** |
| 今日推荐 `recommend/today` | 冷启动（当天首次） | **35.3s** |
| 智能搭配 `recommend/outfits` | 无缓存，每次现算 | **29.8s（ok）/ 55.1s（empty）** |

波动 5 倍以上。同一请求既有 7s 也有 36s，说明**排队/限流占比大于计算本身**。

### 单次调用 token 实测（识图）

| 渠道 / 模型 | 耗时 | prompt | completion | 其中思考链 | 结果 |
|---|---|---|---|---|---|
| lucky / deepseek-v4.1-flash | 16.0s | 1268 | 200 | 119 | 正确 |
| 42w / deepseek-v4-vision | 20.5s | 573 | 66 | — | 正确 |

- 一张 1024px 图的 data URL 约 132KB，占 prompt 的绝大部分。
- `deepseek-v4.1-flash` 是推理模型，输出前会先生成思考链；`max_tokens` 是「思考 + 正文」共用预算。
- 连续请求会返回 **429 `tpm exhausted` / `rps exhausted`**：免费站按分钟限 token。批量录入 26 件 ≈ 3.9 万 tokens，很容易打满。
- 网关不支持关闭思考链：`enable_thinking:false` 直接连接失败，`reasoning_effort:none` 被忽略后仍 429。

## 2. 时间花在哪

```
客户端请求
  ├─ 服务端鉴权 / 查衣物 / 天气（几十 ms，天气有内存缓存）
  ├─ prompt 拼装（<1ms）
  ├─ 网关排队 + 模型思考 + 生成正文   ← 主要耗时，7~55s
  ├─ Zod 解析 + prune + 回填完整衣物（<10ms）
  └─ 今日推荐：写缓存（<10ms）
```

- **识图**：耗时 = 图片 token 注入 + 思考链 + 正文。思考链实测 119 tokens，正文 ~220 tokens；吞吐约 20 token/s，剩余时间在网关排队。
- **今日推荐**：有缓存时几乎零成本；冷启动 = 一次完整生成（35s）。
- **智能搭配**：**完全没有缓存**，每次点 chip 都重新生成（30s+）。
- **失败路径**：推荐路由没配兜底，主路由 429 后同路由重试一次，两次都失败 → 55s 返回 `empty`。

## 3. 优化路线图

每一步独立成任务、独立验收；按顺序做，前一步不阻塞后一步。

### Step 1 智能搭配结果缓存（预期收益最大）

- **目标**：同一用户、同一组筛选条件、同一天内重复请求，耗时从 30s+ 降到 <0.3s。
- **做法**：复用今日推荐的缓存表与 `stale` 机制，缓存键扩展为 `(ownerId, date, season, occasion, style)`；衣橱变化时标记失效。
- **验收**：默认参数连点两次，第二次 <300ms；「换一批」仍能拿到新结果（`forceRefresh` 绕过缓存）；新增当季衣物后旧搭配仍可展示，不强制重算。
- **风险**：低。只影响「智能搭配」页。

### Step 2 路由韧性：兜底 + 429 快速失败

- **目标**：429 时不再空等 55s，快速切到可用渠道；失败率可观测。
- **做法**：给 `RECOMMEND` 配 `FALLBACK_CHANNEL/MODEL`；从 SDK 错误对象取 HTTP 状态码，429 直接切兜底、不原地重试（取不到码按普通失败处理）；日志打点记录「限流」「主路由失败（含状态码）」「切换兜底」。
- **验收**：人为把主模型配错/打满配额，接口在 ~25s 内返回 `ok` 或明确的 `empty`，日志能看到「主路由 429 → 切兜底」。
- **风险**：低。配置 + `AiService` 小改。

### Step 3 识图瘦身：喂图尺寸 + max_tokens

- **目标**：识别耗时下降，tpm 消耗下降，429 概率降低。
- **做法**：
  1. `VISION_MAX_EDGE` 1024 → 768（先不要一次降到 640），JPEG 质量保持 80；
  2. 识别/截图提取 `max_tokens` 4000 → 2000（不要降到 1024，历史踩坑会因思考链吃光而返回空正文）；
  3. 回归 10 件不同品类衣物的识别准确率（品类/主色/厚薄三项）。
- **验收**：同一批图的 prompt tokens 下降 ≥30%，识别 P50 下降 ≥20%，准确率不低于改前（人工判定）。
- **风险**：中。尺寸下降可能影响小配饰/图案细节识别。

### Step 4 今日推荐预热

- **目标**：用户打开首页时尽量命中缓存，避免 35s 冷启动。
- **做法（二选一，需产品确认）**：
  - 客户端登录后异步触发一次 `recommend/today`（不 await，失败静默）；
  - 后端在时段切换时给活跃用户预生成（需要定时任务与成本评估）。
- **验收**：时段切换后首次进入首页，命中缓存占比 >80%（按日志统计）。
- **风险**：中。预热会产生额外 AI 调用成本，需要配额评估。

### Step 5 识别结果哈希缓存

- **目标**：同一张图重复识别（重试、批量重复上传）秒回。
- **做法**：以图片内容 SHA-256 + 品类候选集版本为键，落表或内存 LRU；命中直接返回。
- **验收**：同一图第二次识别 <100ms；不同图不串结果。
- **风险**：低。需明确缓存有效期与「用户分类表变化」的失效条件。

### Step 6 prompt / 输出体积压缩

- **目标**：降低推荐类 prompt 与 completion tokens。
- **做法**：衣橱摘要只保留 id/品类/颜色/厚薄/正式度/风格；默认产出 2 套而非 3 套（或按用户选择）。
- **验收**：同一衣橱的推荐 prompt tokens 下降 ≥30%；生成耗时与 429 次数同步下降。
- **风险**：低，但可能影响搭配多样性。

### Step 7 体验兜底（可与上面并行）

- 识图等待超过 15s 时显示「跳过 AI，先存图后补」显式按钮；
- 今日推荐冷启动显示骨架屏与「正在为你搭配…」进度文案；
- 智能搭配 chip 切换时保留上一次结果，避免空白等待。

## 4. 度量方法（每步改前/改后各跑一次）

1. 识别：同一组 10 张衣物图，串行调用，记录 P50 / P95 / 429 次数 / prompt tokens。
2. 今日推荐：区分「冷启动」与「缓存命中」两组，各 5 次。
3. 智能搭配：默认参数连点 5 次，记录首次与后续耗时、缓存命中率。
4. 所有测量固定在同一时段，避免上游限流时段差异；结果记入本文件附录。

## 5. 上传图片要不要压缩？

**结论：不用为识别速度压缩。**

- 客户端上传的是原图（`uni.chooseImage` 未指定 `sizeType`），但服务端 `urlToDataUrl` 会先 sharp 缩到长边 1024、JPEG 80 再喂模型。实测 1.9MB 原图 → 132KB data URL。
- 上传体积只影响「上传到又拍云」的耗时与存储成本，不影响模型推理。
- 压缩客户端原图会牺牲衣橱主图与抠图质量，收益只是上传快一点，不划算。
- 要省流量，只对 >5MB 的超大图做**保分辨率的质量压缩**；或者交给又拍云图片处理参数。

---

## 6. 不建议做的事

- **流式返回识别结果**：识别输出是单个 JSON，流式对用户体验帮助有限，解析复杂度高。
- **本地小模型做识别**：移动端算力与包体积成本远高于收益。
- **盲目降低 max_tokens**：历史踩坑（1024 被思考链吃光 → 空正文），必须保底 2000 并监控 `finish_reason=length`。
- **在客户端做多级缓存**：服务端缓存 + `onShow` 刷新已够用，客户端缓存会引入一致性问题。
